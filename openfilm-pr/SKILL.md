# OpenFilm PR 工作流

从目标基线读取项目规范、正文模板和 CI 配置。以下是上游入口。[贡献指南](https://github.com/openfilm/openfilm/blob/main/CONTRIBUTING.md) · [PR 模板](https://github.com/openfilm/openfilm/blob/main/.github/pull_request_template.md) · [CI 配置](https://github.com/openfilm/openfilm/blob/main/.github/workflows/ci.yml)

## 1. 任务认领与需求分析

- 读 issue、维护者评论和关联 PR，检查分配、认领与合并状态。在上游目标分支复现，确认问题仍存在且没有重复实现。发现已有修复或活跃的同类 PR 时，先说明情况，再决定是否选择其他 issue。
- 记录上游仓库、目标分支、共同基线提交（merge base）和 fork 分支。已有 PR 时，直接核对其 base 和 head。上游基线用于审查代码，官方稳定版用于对照用户体验，分别记录版本。
- 将需求写成可验收的行为。区分用户报告的现象、已复现的事实、维护者认可的范围和待验证的推测。列出应保留的原行为。获授权后，在 issue 简短说明认领和拟处理的范围。

进入实现前，能给出 issue 链接、复现步骤、基线提交和预期结果。

## 2. 沿用原有接口与工程规范

- 先读相邻组件、调用方和测试。复用项目现有的命名、接口、渲染函数和交互规则。沿用现有目录结构和数据格式。一份 PR 聚焦一项变更。
- 维护者收窄范围时，按最终需求回查旧方案关联的菜单、设置、API、翻译和测试。核对仍需要哪些改动，以及哪些可以撤回到上游实现。
- 行为修复应有回归测试。用户可感知的修复按贡献指南添加相应包的 `patch` changeset，采用英文用户描述。涉及 `film.html` 格式时同步更新 `packages/openfilm/SPEC.md`。
- 用 `git status --short` 找出未跟踪文件和工作区改动，用 `git diff <base-sha>` 看当前相对基线的净差异。逐文件说明改动目的和必要性，并核对 `git diff --check <base-sha>`。已有 PR 的修订可能撤回旧版内容，以最终相对上游的差异判断范围。

进入验证前，每个改动文件都能对应需求、回归测试或发布说明。

## 3. 真实 GIF、测试和逐项核对

- **复现和回归**。走 issue 中的真实操作路径，验证用户可见的结果。涉及画布时同时检查实际绘制或像素、尺寸和控件位置。包含适用的下限、默认值、拉高结果及保留行为。用能在修复前复现、修复后通过的回归覆盖关键行为。
- **对照录制**。UI 改动使用可公开分享的真实素材，以同一设备环境、素材和步骤分别录制原版与修订版。标清所用版本或提交，保留鼠标和实际操作。录制辅助标注应与产品界面区分。检查 GIF 能看清触发操作和结果。
- **验证结果**。记录命令、环境、通过数、失败、跳过和未运行项。区分预期的上游复现失败与真正的回归。本地按改动运行相关测试和检查，例如 `pnpm typecheck`、`pnpm build`、`pnpm audit:public` 与 `pnpm check:pack`。将本地结果与合并前要求通过的 macOS、Windows、Linux CI 分开记录。合成素材只支持其复现条件下的结论。
- **审核材料**。用「要求｜代码位置｜验证证据｜结果」逐项核对。另列「文件｜改了什么｜为什么必要」，交代测试的价值和已有行为是否保留。涉及 UI 时附上两段 GIF。列出尚待验证的事项。

生成 GIF 前先查 [功能索引](scripts/openfilm-gif/README.md)，按当前 PR 要验证的操作和效果选择已有功能。没有合适的功能时，复用顶层录制与转码工具，在 `scripts/openfilm-gif/` 下新建功能子目录，将场景脚本、示例配置和复现说明放在一起。核对输出和实际运行结果后，将脚本、复现说明和更新后的索引一起提交到 skills 仓库。

## 4. 撰写精简、可视化的 PR

- 按项目模板组织正文。标题沿用 `Studio: …`、`CLI: …` 等前缀并说明结果。项目采用 squash merge，PR 标题会成为合并提交标题。正文和回复默认用简洁英文，遵照用户和项目的语言要求。
- 在 `What and why` 关联 issue，写清触发条件、原行为和修复后的变化。修复完整覆盖该 issue 时按模板使用 `Fixes #编号`。有助于评审时，用短公式或少量实测数据说明边界。
- 将测试摘要放在验证部分。UI 修复附原版、修订版两段 GIF，每段旁写一句读图提示。使用审阅者可访问的附件或固定链接，演示素材与代码差异分开。按实际验证结果填写 `Checklist`。
- 更新已有 PR 的正文，使其反映当前方案。回应维护者时，获授权后在原讨论中追加简短回复，说明已处理的意见并链接修订提交。

## 5. 审核后提交与发布验证

- 提交前向用户提供最终差异、逐项核对、测试结果、适用的 GIF 和拟发布正文。收到对当前版本的发布授权后，按项目约定提交。已有授权继续执行。
- 只暂存审核范围内的文件。检查暂存差异，按项目风格写提交标题，推送到已核对的 fork 分支。已有 PR 时更新原 PR，尚无 PR 时，向已核对的上游目标分支新建 PR。
- 打开发布后的 PR 核对标题、正文、提交、Files changed 和 GIF 的实际显示。查看对应提交的 CI 状态。工作流等待维护者批准时，记录为待批准。按用户要求跟进审阅和检查结果。

## 第 471 号 PR 的波形修复

报告提到波形太小，分离音频后也看不清。复现确认纯音频已有缩放，带原声视频的波形画布仍固定为 13px。构造的低振幅样例中，画布变高后波峰仍为 1px。原始素材未验证，因此将低振幅记为可能原因。[Issue #446](https://github.com/openfilm/openfilm/issues/446)

维护者要求移除占比菜单和 `trackWaveforms`，改用固定占比并保留 15px 音频区域下限。本次沿用旧方案的默认值 30%，以及原有波形绘制与控件交互。最终差异仅涉及 `Timeline.tsx`、一个浏览器回归和一个 `patch` changeset。[维护者回复](https://github.com/openfilm/openfilm/pull/471#issuecomment-6915468855)

两段真实素材 GIF 使用同样的缩放操作。视频轨道从 36px 拉到 156px，稳定版的画布保持 13px，修订版从 13px 增至 40px。纯音频在两版均从 27px 增至 107px。完整正文和对照演示见已合并的 PR。[PR #471](https://github.com/openfilm/openfilm/pull/471)

这两段 GIF 可用目录 `scripts/openfilm-gif/` 中的录制器重录。选择 `waveform-height` 场景，对比官方 0.3.2 与 #471 的修订版。[场景脚本](scripts/openfilm-gif/waveform-height/scenario.mjs) · [复现步骤](scripts/openfilm-gif/waveform-height/README.md)
